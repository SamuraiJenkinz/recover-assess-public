Output: core/throttle.py, retry wiring in graph.py, FakeGraph.throttle, two test modules.
</objective>

## Flagged assumptions

- **RESEARCH A10 (surface to developer):** only 429 and 503 are retried. Transient 500, 502 and 504 responses and transport errors (connect failures, timeouts) fail the call immediately; the spec is silent on them. If the pilot shows transient 5xx, adding them is a one-line change to RETRYABLE_STATUSES plus tests.
- **RESEARCH A6:** Retry-After may be an HTTP-date as well as seconds; both are parsed.
- **RESEARCH A7:** one ThrottledOut type with reasons retries_exhausted, budget and breaker; a tripped breaker poisons the session. Phase 3's run-state mapping may split them (RESEARCH Open Question 2, resolved: tests assert the reason, so the causes stay distinguishable).
- **Invariant (handoff to Phase 3):** the ThrottleGate is per GraphClient, so tenant-wide coordination holds only if a run builds exactly one GraphClient and opens every site's session from it (recorded in Plan 01-09 and SKELETON.md).
- **RESEARCH A11:** FakeClock advance-on-sleep is adequate; tests assert ordering bounds, not exact interleaving.
- **Not modelled (PITFALLS #7):** resource-unit token buckets, x-ms-resource-unit tracking and the decorated User-Agent's effect on priority are out of Phase 1 scope (GRPH-05 does not require them); the UA string itself lands in Plan 01-09.
